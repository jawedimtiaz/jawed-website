User, Device or Service? A Simple Way to Scope IT Issues

A simple framework for deciding whether an IT problem is primarily associated with a user, a device or a shared service before deeper troubleshooting.

Published: 2026-09-27 · Updated: 2026-10-12

Why scope matters

The same symptom can have very different causes. Identifying the likely scope early helps avoid unnecessary changes and gives you a clearer troubleshooting path.

Start by asking whether the problem follows the user, the device or the service.

If it looks user-specific

Consider whether the issue follows the person's account, permissions, profile or workflow. Where policy allows, a controlled comparison can help distinguish a user-specific problem from a wider service issue.

  • Does the same user experience the issue elsewhere?
  • Does another user work normally on the same device or service?
  • Is the problem tied to one account or workflow?

If it looks device-specific

If the issue remains with one device while the same user or service works elsewhere, investigate the device state and configuration.

  • Is the device connected and responsive?
  • Does the issue occur across relevant applications?
  • Does a known-good comparison point to the device?

If it looks service-wide

When multiple users or devices experience the same behavior, consider a shared service or infrastructure issue before changing individual devices.

  • Are multiple users affected?
  • Did the problem begin around the same time?
  • Is there an existing service or incident notification?

Use scope to guide the next test

Scoping is not the final diagnosis. It is a way to choose the next useful test while avoiding unnecessary changes.

After each test, update your working hypothesis and document what the result tells you. If the evidence points outside your support scope, escalate with that evidence.

A quick scope decision table

Pattern observedWhat it suggestsNext useful check
One user is affected across more than one approved device or sessionA user, identity, permission or workflow-specific path is worth checkingVerify the exact sign-in/application context and approved access status; do not ask for passwords or MFA codes
Different users have trouble on the same deviceThe device, local configuration or shared session may be involvedCompare relevant application behavior and device state within support permissions
Several users or devices report the same service symptom around the same timeA shared service, dependency or wider incident becomes more plausibleCheck the approved service-status or incident channel and capture the common time window
Only one application fails while other tasks workThe failure may be specific to the app or one of its dependenciesCapture the app's exact error and test an approved comparison before changing device settings

These patterns are clues, not proof. A user and a device can both be affected by a shared service issue, and different symptoms can coexist.

Worked example: one user cannot open an app

Illustrative scenario only; not a report of a real incident. A user reports that a business app fails to open. Other expected apps work on the same device.

  1. Record the exact error, time, application and task that fails.
  2. Check whether the issue is limited to this user or whether other authorized users report the same symptom.
  3. If permitted, compare the same user's workflow through an approved alternative or check a known service-status channel.
  4. Use the comparison to choose the next question. Do not conclude that the network, account or app is definitely the cause based on one test.
  5. Make only an approved, evidence-based change, then retest the original task. If access policy or elevated permissions are involved, escalate with the evidence.

Boundaries and stop conditions

Do not switch users into accounts they are not authorized to access, collect passwords or authentication codes, disable security controls, remove device management, or make broad configuration changes simply to test a theory. Follow approved procedures and stop when the next step exceeds your permissions or risks data loss.
